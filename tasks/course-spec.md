# Spec: Deterministic JavaScript Foundations

Status: proposed course contract. No implementation should begin until this document and the first lesson content are approved.

## Objective

Kolibri should teach through a fixed, challenge-driven loop:

1. Read one short explanation.
2. Edit a small starter program.
3. Run authored behavioral checks.
4. See the first concrete failure or a pass result.
5. Fix or reset, then unlock the next challenge.

A new learner must be able to complete the first lesson without an account, email, model call, or prior programming knowledge. Kolibri’s personal-problem project work remains a later track after the foundations loop is proven.

“Deterministic” means that the rendered lesson, test result, progression decision, and saved state are functions only of the authored course data, the learner’s current code, and persisted progress. No random values, wall-clock dates, network responses, autoplay timers, or generated grading rules may affect them.

## Current repository evidence

- index.html is generated by build-page.js; app.js imports page-content.js and currently drives a scripted, read-only three-stage marketing demo.
- server.js serves static files and the existing waitlist API. It has no course state or authentication.
- COURSE.md, PLAN.md, and lessons/week0.md currently describe an interview-first, project-first course. They must be reconciled with this contract before implementation; they are not parallel sources of truth.
- Existing zero-dependency verification is Node syntax checks, node server.js --selftest, and node demo-smoke.mjs.

## Assumptions

1. V1 targets current desktop and mobile browsers with JavaScript enabled.
2. V1 contains one JavaScript course, one module, one lesson, and three challenges.
3. The editor is a native labeled textarea; no editor dependency is added.
4. Challenge tests are visible behavioral contracts, not hidden anti-cheat tests. The course makes no certificate or high-stakes assessment claim.
5. The waitlist endpoint remains unchanged and receives no learner code or progress.

## Course hierarchy and IDs

The authored hierarchy is fixed and addressable:

| Level | V1 ID | Rule |
|---|---|---|
| Track | js | Contains courses in a language track. |
| Course | js-foundations | Contains ordered modules. |
| Module | js-foundations-m01 | Contains ordered lessons. |
| Lesson | js-foundations-m01-l01 | Contains ordered challenges. |
| Challenge | js-foundations-m01-l01-c01 | One observable learning objective. |

Every node has a stable unique id, title, and contiguous position. Challenge order is authored, not sorted from user state. A prerequisite must exist and appear earlier in the same course.

## Canonical content contract

The learner-facing course data is static and validated before it is built. Each challenge has:

| Field | Required contract |
|---|---|
| id | Stable unique ID. |
| position | Integer position with no gaps. |
| title | Concrete action-oriented title. |
| concept | Exactly one primary concept; must exist in the lesson glossary. |
| prerequisites | Existing earlier challenge IDs, or []. |
| instruction | Exact learner task; no undefined terms. |
| starter | Exact initial editor buffer; it must fail at least one authored check. |
| tests | At least one typed behavioral check with an ID, expected value, and failure message. |
| hints | Ordered nudge, direction, and walkthrough text. Hints never unlock a challenge. |
| nextId | Next challenge ID or null for the lesson’s final challenge. |
| feedback | Pass text and named failure text for every check/error path. |

V1 test types are deliberately finite:

- console-lines: exact captured console.log lines.
- app-text: exact #app.textContent after execution.

CRLF is normalized to LF; values are then compared as exact strings or arrays. Extra output is a failure unless the challenge explicitly declares an output allowance. Tests assert observable behavior, never source-code regexes.

Author-only fixtures live outside the learner bundle and provide at least one reference solution, one semantically different valid solution, and named wrong cases for every challenge. The validator runs all fixtures against the same authored test descriptors. Solutions are not required for runtime grading.

The lesson itself has an objective, glossary, ordered challenge list, and exact completion copy. The validator requires every instruction term to exist in the glossary or an earlier challenge, every challenge to have at least one pass fixture and one failing fixture, and every authored field used by the UI to have non-empty copy. This is the content coverage gate: explanation → example → task → test → failure feedback → hint sequence → pass feedback → next challenge.

Course: js-foundations → module “Values and output” → lesson “Variables and output”.

| Challenge | Concept | Required behavior |
|---|---|---|
| js-foundations-m01-l01-c01 | const, strings, and output | Print exactly Hello, Ada. The starter prints the wrong value. |
| js-foundations-m01-l01-c02 | let, reassignment, and numbers | Update a count and print exactly 3. The starter prints the wrong value. |
| js-foundations-m01-l01-c03 | arrays and DOM output | Render an authored list into #app with exact text. The starter renders incomplete output. |

Comments are encouraged in the lesson but are not statically graded. Free-form explanations and the personal-project review log belong to the later project track unless a manual-review surface is deliberately added.

## Challenge runtime contract

The parent page sends only { type, runId, challengeId, code } to a fresh runner. The runner returns a versioned result containing runId, challengeId, ok, per-check results, and a sanitized error object. The parent accepts a result only when its source is the current runner and its runId is current; late results are ignored.

The result shape is fixed:

~~~json
{
  "version": 1,
  "type": "result",
  "runId": 7,
  "challengeId": "js-foundations-m01-l01-c01",
  "ok": false,
  "checks": [{ "id": "console-output", "pass": false, "actual": ["Hello"], "expected": ["Hello, Ada"], "message": "Print the complete greeting." }],
  "error": null
}
~~~

The browser runner and Node authoring validator use the same typed test-descriptor interpreter and normalization rules. They do not maintain separate copies of grading semantics.

The runner:

- Uses an iframe with sandbox="allow-scripts" only. It does not grant same-origin access, forms, modals, top navigation, or downloads.
- Uses a restrictive CSP: default-src 'none'; script-src 'unsafe-inline'; style-src 'unsafe-inline'; connect-src 'none'; img-src 'none'; form-action 'none'; base-uri 'none'. Learner code cannot access the parent DOM, cookies, localStorage, secrets, or server endpoints.
- Caps learner code at 50 KiB, captured output at 64 KiB, and one run at 2 seconds. These are failure limits, not scores.
- Is replaced or removed on timeout so an infinite loop cannot freeze the course UI.
- Reports syntax and runtime errors as learner-facing file/line feedback without exposing stack traces or internal details.
- Never inserts learner output as HTML. User output is rendered with text nodes or escaped text.

## State machine

Each challenge has one derived UI state:

| Event | Transition | Required effect |
|---|---|---|
| OPEN | LOCKED → READY | Allowed only when prerequisites pass; load starter or draft and focus editor. |
| INPUT | READY/FAILED → READY/FAILED | Save draft; do not change mastery. |
| RUN | READY/FAILED → RUNNING | Increment runId, disable duplicate runs, start timeout. |
| RESULT(ok) | RUNNING → PASSED | Save code and mastery; unlock only nextId; announce pass. |
| RESULT(fail/error/timeout) | RUNNING → FAILED | Save draft; show first failing check/error; unlock nothing. |
| RESET | READY/FAILED → READY | Restore exact starter and clear only the current draft. |
| NEXT | PASSED → READY or lesson COMPLETE | Move to the authored next ID and persist it. |
| RELOAD | storage → derived state | Never restore RUNNING or a stale failure; derive from validated progress. |
| INVALID_RESULT | any | Ignore without changing UI or progress. |

Mastery is monotonic: once a challenge is passed, resetting or revisiting it never revokes that pass. A passed challenge is review-only in V1. No retry cap, timer-based score, partial unlock, or skip path exists.

Completion copy is exact and modest: “You finished the JavaScript Foundations preview — 3 challenges.” It must not claim the full course, a certificate, an account, or a live project.

## Progress contract

Storage key: kolibri.progress.v1.

~~~json
{
  "version": 1,
  "courseId": "js-foundations",
  "currentChallengeId": "js-foundations-m01-l01-c02",
  "passedIds": ["js-foundations-m01-l01-c01"],
  "drafts": { "js-foundations-m01-l01-c02": "const count = 2;" }
}
~~~

- Save drafts after input and mastery after pass, reset, and next.
- Wrap storage access and JSON parsing in try/catch. Corrupt or incompatible data becomes a fresh valid state.
- If storage throws, continue in memory and show that progress will not survive reload.
- Sanitize IDs against the authored course before using them.
- Reflect the current challenge in the URL hash. Invalid or locked deep links resolve to the first incomplete challenge without clearing drafts.
- Browser back/forward changes the derived view; it never fabricates a pass or erases progress.

## Accessibility and interaction contract

- Every editor has a visible label, visible focus, undo/redo, and at least 16px text on mobile.
- Locked challenges are disabled with a text explanation and aria-disabled; no fake clickable controls.
- On open, focus the editor. On Run, move focus to feedback. On pass, focus Next; on failure, return focus to the editor.
- Feedback uses role=status or aria-live and text labels, never color or animation alone.
- Run is keyboard-triggerable; reduced motion does not remove content or status.
- Mobile layout exposes the same editor, Run, Reset, feedback, hints, and progression controls without horizontal scrolling.

## Project structure and source of truth

Planned implementation files:

- course-content.js — learner-facing authored hierarchy and challenge descriptors.
- course/fixtures/ — author-only reference and wrong-answer fixtures.
- course-validate.mjs — schema, ordering, fixture, and content QA checks.
- challenge-runner.html — isolated execution document.
- app.js, build-page.js, styles.css, index.html — course UI and generated markup.
- server.js, demo-smoke.mjs, and CI — security, build, and runtime gates.

The existing lessonDemo and its autoplay timers remain a marketing demonstration, not the graded course runtime. Existing project-first docs are updated or explicitly marked historical in the same implementation phase so no two course contracts remain. V1 hints never include a complete pasted solution; the author-only fixtures are never shipped to the learner runtime.

## Commands and testing strategy

Before implementation, the current baseline remains:

~~~sh
node --check app.js
node --check build-page.js
node --check server.js
node server.js --selftest
node demo-smoke.mjs
~~~

The course gate adds:

~~~sh
node course-validate.mjs
node build-page.js
node build-page.js
~~~

The second generation must be byte-identical to the first. course-validate.mjs must fail on duplicate or missing IDs, broken prerequisites or nextId, undefined glossary terms, empty feedback or hints, a passing starter, absent wrong-case coverage, or a reference solution that fails. It must also verify the authored coverage matrix and that generated app/style URLs match the current content hashes. demo-smoke.mjs must cover fail/pass/unlock order, syntax/runtime/timeout errors, stale runId, reset, draft reload, corrupt/throwing storage, URL navigation, keyboard/status markup, sandbox attributes, blocked network/parent access, escaped output, and honest completion copy.

## Boundaries

- Always: authored IDs and descriptors, behavior-based checks, deterministic normalization, isolated execution, escaped output, guarded storage, accessible status, and the full zero-dependency gate.
- Ask first: adding a dependency, changing the waitlist/API, storing learner data server-side, changing the runtime sandbox policy, or making completion/certificate claims.
- Never: execute learner code in the parent page, use learner input as HTML, grade with a model or random hidden rule, persist secrets, or claim the preview is the full course.

## Success criteria

The spec is implemented only when a clean checkout can validate the complete authored course, a learner can pass, fail, reset, and reload the three challenges deterministically, no later challenge unlocks early, unsafe runner actions are contained, and the generated page plus all existing checks are reproducible.
