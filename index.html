KOLIBRI / ONLINE COURSE

Learn programming by changing something that works.

Kolibri is an online, self-paced programming course built around short explanations, interactive tasks, immediate checks, and projects that grow with the learner.

Follow the build

Learn by changing something

Kolibri is being designed as a sequence of short lessons, interactive tasks, and projects completed in the browser. A lesson may introduce one idea, show a small piece of an existing system, and ask the learner to change it. The result can be checked immediately, so mistakes become part of the next step instead of something discovered several hours later.

Some tasks will involve writing code. Others may involve reading unfamiliar code, finding the cause of an error, choosing between several approaches, changing a prompt, inspecting output, or explaining why a solution works. The course should not reduce programming to filling blanks, but it also should not leave a beginner alone with an empty editor and a vague project brief.

As the learner progresses, the tasks should become less controlled. Early lessons may provide most of the structure. Later lessons may only provide the problem, constraints, tests, and a partially working system. The learner gradually becomes responsible for more of the decisions.

The curriculum gets less helpful over time

The beginning of Kolibri should be fairly guided. Learners need enough structure to become comfortable with files, code, Git, terminals, debugging, APIs, and deployment without spending the first week configuring tools they do not understand.

The course should gradually remove that structure. Later sections should contain incomplete systems, ambiguous errors, competing solutions, and projects where there is no single expected implementation. The point is not to make every task harder for its own sake. It is to transfer more of the judgment from the course to the learner.

Projects begin inside the course

Portfolio work should not appear only as a final assignment after dozens of disconnected lessons. Smaller projects can begin inside the curriculum and grow as the learner gains more control. A tool built during one module may return later when the learner adds storage, an API, deployment, tests, or a better interface.

The final portfolio project should ask the learner to combine what they have practiced without following a complete tutorial. Kolibri may provide constraints, checkpoints, automated tests, examples of scope that is too large, and feedback on common failures. The project itself should still belong to the learner.

Where possible, a completed project should produce something that can be opened through a public link, inspected in a repository, and described in the learner's own words.

INSIDE A LESSON

Change a small working tool and understand the path from input to output.

RETURN LATER

Add the difficult parts

Bring the same project back for storage, external APIs, tests, deployment, and interface decisions.

OWN THE RESULT

Publish and explain it

Share a live link and repository, then describe the tradeoffs in your own words.

Feedback should explain the failure

A failed check should not only display a red mark or reveal the correct code. Kolibri should tell the learner what kind of requirement was not met, point toward the relevant part of the system, and preserve enough uncertainty that the learner still has to investigate.

Hints may become more specific after repeated attempts. The first hint can identify the area of the problem. A later hint can suggest what to inspect. The completed solution should remain available, but reaching it should not be the easiest way through every lesson.

When a task cannot be checked reliably with automated tests, the course can ask the learner to compare outputs, explain a decision, inspect a deployment, or submit a small artifact.

Check failed

The expected greeting was not returned for the name provided by the caller.

What to inspect next

The function still returns the same text for every input. Find where the name parameter is available and trace how the return value is constructed.

AI is available, but it does not complete the course for you

Kolibri can include an AI assistant that has access to the current lesson, the learner's code, previous attempts, and the relevant error output. It should help the learner inspect the problem rather than immediately replacing the work with a finished answer.

The assistant may ask what the learner expected, explain an error, point toward a file, compare two approaches, or generate a smaller example. It should not silently rewrite an entire project whenever a test fails.

The learner should also encounter tasks where AI output itself must be reviewed, corrected, tested, or rejected. Using AI is part of the material, not a shortcut around it.

LEARNER

The test says the value is undefined, but I return the message.

KOLIBRI ASSISTANT

Which function does the test call? Compare that name with the function you edited before changing more code.

Progress means completed work

Progress should be based on lessons completed, checks passed, projects deployed, and explanations submitted. Avoid meaningless engagement metrics.

The course should save work automatically and allow learners to return to an unfinished task. A dashboard may show the current module, recent work, project status, saved notes, and the next available lesson.

Certificates may be added later, but the page should not make them the main reason to complete the course.

What exists now

Kolibri is still being built. The material comes from programming lessons I have already taught directly and from the problems I have seen while helping people build portfolio projects. The online curriculum, lesson system, automated checks, and course interface are the next part of the work.

The earlier “vibe coding dari nol” classes were in-person teaching experiments that exposed where beginners became confused. That work informs Kolibri, but the current product direction is an online course learners can use independently in the browser.
